# Better TNT 2.0

大量の TNT による TPS 低下を抑える Forge Mod。Minecraft 1.16.5 / 1.20.1 を Stonecutter で 1 つのソースから出す。

機能は「バニラとの違い」で 4 種類に分かれる。

| 種類 | 機能 | 既定 |
|---|---|---|
| **バニラと完全に同じ結果** | 処理の高速化 (レイ・遮蔽判定・TNT の当たり判定)、露出度キャッシュ | オン |
| **サーバーが重いときだけ、タイミングが変わる** | 爆発の分散 (throttle) | オン |
| **見た目・音だけ変わる** | 爆発パケットの軽量化 | オン |
| | 爆発エフェクトの上限 | オフ |
| **爆発の結果が変わる** | レイの本数を減らす | オフ |

## 1. バニラと完全に同じ結果になる高速化

JFR でバニラの爆発を計測したところ、サーバースレッドの時間の内訳は次のとおりだった (6875 個の TNT、Mod の機能はすべてオフ)。

| 処理 | 割合 | 対策 |
|---|---|---|
| `getSeenPercent` (エンティティへの遮蔽判定レイ) | 27% | 空気ブロックはその場で通過させ、チャンクは直接引く |
| 1352 本のレイのブロック参照 (`getBlockState` / `getFluidState`) | 21% | レイは 0.3 ブロックずつ進むので、同じブロックを約 3 回続けて参照する。直前のブロック・流体・爆発耐性を使い回し、流体はブロックの状態から取る |
| 壊すブロックの `HashSet<BlockPos>.add` | 13.5% | 同じ座標が何度も追加される。直前と同じ座標はスキップし、`long` の集合で重複を先に落とす |
| 点火済み TNT の移動時のエンティティ当たり判定 | 15% | 周囲の全エンティティを列挙してから「当たれない」と捨てていた。当たれるエンティティ (ボート・シュルカーなど) だけをワールドごとに管理して、それだけを調べる |

チャンクの参照は 4×4 チャンク分を、爆発 1 回の処理中だけキャッシュする (tick をまたいで持たない)。

さらに**露出度キャッシュ**: `getSeenPercent` の結果を (ワールド, 爆心, エンティティの当たり判定) をキーに覚えておく。同じ場所に積まれた TNT はすべて同じ結果になる。
ブロックが壊れたら捨てる。

**検証**: 検証モード (`-Pverify`、下記) で、高速化したすべての処理をバニラの処理と並べて比較した。ボート・シュルカー・水を含む TNT 試験で、
1.16.5 と 1.20.1 のそれぞれ 3 億回以上 (開発環境と本番の Forge サーバーの両方) 比較して、不一致は 0 件。

途中で見つかった差分: 1.16.5 では削除されたエンティティ (壊れたボートなど) が tick ループで処理されるまでチャンクに残り、その間もバニラは衝突判定に含めていた。
この挙動も再現している (1.20.1 は削除と同時にリストから外れる)。

## 2. 爆発の分散 (throttle) — サーバーが重いときだけバニラと変わる

現在の tick がすでに `maxTickMillis` (既定 40ms、1 tick は 50ms) かかっていたら、それ以降の爆発を後の tick に回す。
**サーバーが処理しきれている間は 1 つも回さないので、バニラと同じ。** 例: TNT 500 個の連鎖では 94 個が回された (そこだけ tick が 40ms を超えた)。

回された爆発は、`ServerLevel.explode` の呼び出しを引数ごと保存して、後の tick で同じ呼び出しをやり直す。
Forge の `ExplosionEvent`、ブロック破壊、ドロップ、クライアントへのパケットはバニラと同じ経路で動く。順番は先入れ先出し。

### 回された爆発がバニラと違う点
| 違い | 内容 |
|---|---|
| タイミング | 数 tick ～数秒遅れる。**TNT キャノンなど、同じ tick に爆発することを前提にした装置は、サーバーが重いときに正しく動かない** |
| TNT の見た目 | 点火済み TNT は消え、爆発は後から起きる (その間は何も見えない) |
| 押し出し | 消えた TNT は、その間に起きた他の爆発で押されない。爆発の位置は元の TNT の位置のまま |
| エンティティ | 爆発は保存した座標で起きる。その間に動いたエンティティは、動いた先で爆発を受ける |
| 停止・クラッシュ | 通常の停止ではキューを全部実行する (`flushOnShutdown`)。**クラッシュするとキューの爆発は失われる** (TNT はもう消えているので、再起動しても起きない) |
| 戻り値 | 回された呼び出しは、何もしない `Explosion` を返す (`getToBlow()` は空)。この値を使う Mod があれば影響する |

### `tntWaitsInWorld = true` (オプション)
点火済み TNT を消さずに、ワールドに残したまま待たせる (点滅したまま、ワールドと一緒に保存され、クラッシュしても再起動後に爆発する)。
その代わり:
- 待っている間も他の爆発に押され続けるので、バニラより**遠くまで飛ばされてから爆発する**ことがある。
- 残った TNT エンティティの処理が増える。6875 個の試験で最低 TPS が 20 → 16 (1.20.1)、11 (1.16.5) に下がった。

既定では、爆発の位置を保てて軽いキューを使う。

## 3. 見た目・音だけ変わる (clientEffects)
- **`leanExplosionPackets` (既定オン)**: 爆発パケットから、壊れたブロックの一覧を外して送る。
  クライアントは同じブロックを通常のブロック更新パケットでも受け取るので、二重に処理していた。外すと、ブロックが消えるのが爆発の音より最大 1 tick 遅れる。
  通信量とクライアントの負荷が減る (クライアント側の効果は未計測)。
- **`maxExplosionEffectsPerPlayerPerTick` (既定 0 = 無制限)**: 1 プレイヤーあたり 1 tick に送る爆発の音・パーティクルの上限。
  そのプレイヤーを吹き飛ばす爆発は、上限を超えても必ず送る (吹き飛びはパケットで伝えるため)。

## 4. 爆発の結果が変わる (gameplay)
- **`explosionRayGrid` (既定 16 = バニラ)**: 爆発が壊すブロックを探すレイの格子。12 にするとレイが 1352 本 → 728 本になる。

  | | 爆発のピーク tick | 壊れたブロック (TNT 16 個) |
  |---|---|---|
  | 16 (バニラ) | 100 ms | 石: 387 / 土: 3582 |
  | 12 | 81 ms | 石: 384 / 土: 3249 (−9%) |

  遠くまで届く爆発ほどレイの間隔が開き、クレーターの縁に穴が残る。Mod の大きな爆発ではもっと目立つ。

## 測定 (専用サーバー、`/forge tps` の平均 tick の最大値)

| シナリオ | バニラ | 高速化のみ (分散オフ) | 既定設定 |
|---|---|---|---|
| 25×11×25 = 6875 個の TNT ブロックに点火 (1.20.1) | 181 ms / 最低 5.5 TPS | 97 ms / 10.3 TPS | 41 ms / 20 TPS |
| 同上 (1.16.5) | 184 ms / 5.4 TPS | 100 ms / 10.0 TPS | 41 ms / 20 TPS |
| 同じ座標に TNT エンティティ 2000 個 (1.20.1) | 112 ms / 8.9 TPS | 25 ms / 20 TPS | — |

既定設定では 6875 個がおよそ 16 秒で爆発し終わる (バニラは TPS が落ちるので約 25 秒)。

## 旧版 (1.0.0) からの修正点

| 旧版の問題 | 原因 | 2.0 |
|---|---|---|
| 後回しにした爆発でブロックが壊れない | `explode()` だけ呼び直していて、ブロックを壊す `finalizeExplosion()` を呼んでいなかった | 呼び出し全体をやり直す |
| 後回しにした爆発の音とパーティクルが即座に出る | `Start` イベントの時点ではもうパケット送信が確定していた | 上限超過時は `Explosion` 自体を作らない |
| 設定ファイルが効かない | `BUILDER.build()` を `define()` より前に呼んでいて spec が空。上限値も 100 で固定 | 設定項目を定義してから spec を作る |
| 専用サーバーで起動しない | クライアント専用クラス (`DebugOverlayGui`) への Mixin を共通の Mixin 一覧に入れていた | F3 表示は Forge のイベントで、クライアントでのみ登録 |
| 爆発のカウントがずれる | `ExplosionEvent` (Start と Detonate の両方) で数えていた。tick の START と END の両方で減算していた | 実際に走った爆発だけを数える |
| 後から起きた爆発が先に処理される | `push`/`pop` で LIFO になっていた | FIFO |
| サーバーが重くなくても爆発を後回しにする | 1 tick 100 個の固定上限 | tick の処理時間が上限を超えたときだけ |
| 停止時にキューの爆発が消える | — | 停止時に全部実行 (設定で破棄にもできる) |

## 設定
`<world>/serverconfig/bettertnt-server-config.toml`

| キー | 既定値 | 内容 |
|---|---|---|
| `throttle.enabled` | true | 分散処理を使うか |
| `throttle.maxTickMillis` | 40.0 | tick がこの時間を超えたら爆発を回す (0 でオフ) |
| `throttle.maxExplosionsPerTick` | 0 | 1 tick の爆発数の上限 (0 でオフ)。設定すると軽いサーバーでもバニラと変わる |
| `throttle.maxExplosionMillisPerTick` | 0.0 | 1 tick に爆発へ使う時間の上限 ms (0 でオフ) |
| `throttle.minExplosionsPerTick` | 4 | 1 tick に必ず通す数 (他の原因で重いときも進むように) |
| `throttle.tntWaitsInWorld` | false | 回した TNT をワールドに残して待たせる (上記) |
| `throttle.flushOnShutdown` | true | 停止時にキューを全部実行する (false なら破棄) |
| `exposureCache.enabled` | true | 露出度キャッシュ |
| `optimizations.fastExplosionRays` | true | レイのブロック参照の使い回し |
| `optimizations.fastExposureRaycast` | true | 遮蔽判定レイの高速化 |
| `optimizations.fastTntCollisions` | true | TNT の移動時の当たり判定の高速化 |
| `clientEffects.leanExplosionPackets` | true | 爆発パケットからブロック一覧を外す |
| `clientEffects.maxExplosionEffectsPerPlayerPerTick` | 0 | 1 プレイヤー 1 tick あたりの爆発エフェクト上限 (0 で無制限) |
| `gameplay.explosionRayGrid` | 16 | レイの格子 (16 がバニラ、8～16) |

`optimizations` はバニラと同じ結果になるので、普段は切る必要はない。爆発を書き換える別の Mod と相性問題が出たときの切り分け用。
Canary / Radium (Lithium の Forge 移植) が入っている場合は、同じ箇所を書き換えるので `optimizations` と `explosionRayGrid` の Mixin は自動で無効になる。

## コマンド (OP 権限 2)
- `/bettertnt` — 直前の tick の爆発数と処理時間、待っている TNT の数、キューの数、キャッシュのヒット率、省いたエフェクトの数
- `/bettertnt flush` — キューを今すぐ全部実行
- `/bettertnt clear` — キューを破棄

シングルプレイでは F3 画面にも出る。

## ビルド
```
./gradlew "1.20.1:build" "1.16.5:build"
```
成果物は `versions/<mc>/build/libs/`。`./gradlew buildAndCollect` を使うと `build/libs/<version>/` にまとめて置かれる。

開発用の起動: `./gradlew "1.20.1:runClient"` / `"1.16.5:runServer"` など。実行ディレクトリは `versions/<mc>/run` で、バージョンごとに分かれている。
`runServer` はコンソール入力を受け付けるので、コマンドをパイプで流し込んで負荷試験ができる。

- `-Pverify` — 検証モード。高速化したすべての処理でバニラの処理も実行し、結果を比較する。`/bettertnt` に項目ごとの「比較回数/不一致数」が出る。かなり遅い。
  本番のサーバーでも `-Dbettertnt.verify=true` で使える。
- `-Pjfr=<path>.jfr` — JFR でプロファイルを記録する。

### ツールチェーンのメモ
- Stonecutter は **0.7.11** に固定している。0.8 以降は Gradle 9 が必要で、ForgeGradle 6 は Gradle 9 で動かない。
- Gradle は Java 21 で動かす (`gradle/gradle-daemon-jvm.properties`)。コンパイルは 1.16.5 が Java 8、1.20.1 が Java 17 (toolchain)。
- IDE で編集するバージョンを切り替えるには Stonecutter の `Set active project to <ver>` タスクを使う。コミットは 1.20.1 をアクティブにした状態で行う。
- 1.16.5 の ForgeGradle は official マッピングでも**クラス名が MCP のまま** (`ServerWorld`、`Vector3d` など)。メソッド名だけが Mojang 名になる。
